# Arty API

Everything Arty can do, for your own apps. Home network: http://192.0.2.13:8081. Anywhere: https://arty.example.com, which also needs the Cloudflare Access service-token headers (`CF-Access-Client-Id`, `CF-Access-Client-Secret`).

- Base URL: `http://192.0.2.13:8081`
- Key: `Authorization: Bearer <ARTY_API_KEY>`. Use your brain's API key: `provision.sh` saves it to `/srv/ai/secrets/arty-api.txt` on the machine running the brain.
- Errors: `{"error": {"message": "..."}}` with a matching HTTP status.

## Chat (OpenAI-compatible)

Any OpenAI client library works: set `base_url` to `http://192.0.2.13:8081/v1` and the key above.

`POST /v1/chat/completions`

```json
{"model": "Arty", "messages": [{"role": "user", "content": "What's on my server?"}]}
```

- `model`: `Arty` uses the main model (the old name `assistant-core` still works); `arty/<model>` (e.g. `arty/mimo-v2.6:9b`) uses that model for this request only. `GET /v1/models` lists them.
- `GET /v1/models?all=1` lists every downloaded chat model. A request sending `X-Arty-Client-Tools: 1` and `X-Arty-Any-Model: 1` may name any of them; a model that isn't downloaded or only makes embeddings is a 400, and the engine being down is a 503. See [Who Can Run Arty's Tools](tools-trust-boundary.md). Each entry carries `context_tokens` (the context window the brain gives that model: `options.num_ctx` in brain.json, or the model's own size from `model_windows.num_ctx` when `model_windows.enabled` is true; it ships off, ready with 49152 for mimo-v2.6:9b. With it on, sizes differ per model, so a client should use the entry for the model it is sending to, not the smallest) and `reply_tokens` (the most tokens one agent turn reply can use, thinking included: `agent_options.num_predict`, else `options.num_predict`, else 2048). A client should keep at least `reply_tokens` of the window free when it sizes its prompt. Models of an outside OpenAI-compatible server that ArtyEngine serves as `remote/<server>/<model>` are listed too, and never make the brain unload models on the card.
- Every model entry in `GET /v1/models` (with or without `all=1`) carries `available`: false when ArtyEngine says the model is offline (its outside server can't be reached, or the server itself marks the model unavailable). Such an entry's `description` starts with "offline" and the usual list's `name` ends in ", offline)"; the apps show it as "(offline)" in their model pickers.
- `client` (optional, on chats and chat jobs): your app's name, such as `desktop`, `voice`, `telegram` or `discord`. Lowercase letters, digits, `_` and `-`, up to 32 characters.
- `features` (optional, on chats and chat jobs, a list of strings): what the calling app can show. The Android app sends `client` `phone` with `features` `["device_actions", "camera"]` and then gets alarm, timer, app and camera actions (`<phone-action>` lines with kind `alarm`, `timer`, `app` or `camera`). A `phone` client without both (Android 1.5.8 and older) gets only `call` and `text` actions, as before.
- Arty adds its persona, long-term memory, recent conversations and all its tools itself, and remembers the exchange. Send only your app's messages; a `system` message is added as extra instructions.
- The reply has the usual `choices[0].message.content`, plus `tools_used`.
- Arty Auto: `model` set to `auto` picks the model for each message with fixed rules, no extra model call. A picture or video in the latest message is the `vision` role (the `vision_model`, as the `Arty` entry routes pictures), code-heavy text the `code` role (the `coding_model` under the same rule as `Arty`: a big job, or the coding model already loaded), asks about the phone, home, reminders, calendar, music, weather or news (and a voice note) the `agent` role, anything else the `chat` role; `agent` and `chat` both run on the main model with Arty's tools. `route_picture_chats`, `route_coding_chats`, `arty_models` and the other model limits apply as for `Arty`. `GET /v1/models` names it in a top-level `auto` object (`id`, `name` "Arty Auto", `description`, `roles`); the `data` list is unchanged.
- Every chat reply (and the last streamed chunk, and a finished chat job) carries an `arty` object: `model` (the model the turn was set to run on), `role` (the Auto role, else null), `auto`, `context_window` (the window that model gets: the brain's `num_ctx` for it, capped at the model's trained length from the engine's `/api/show`), `steps` (tools used) and, when the engine reported them for the last model call, `usage`: `prompt_tokens`, `completion_tokens`, `context_tokens` (the two added: how much of the window that call used), `cached_tokens` (only when the engine reports `prompt_eval_cached_count`) and `tokens_per_second` (from `eval_count` and `eval_duration`). A running chat job shows `arty` with the pick as soon as it is made. Turns answered by the add-on, a solo model or agent mode have no `model`. The OpenAI-style `usage` also gains `prompt_tokens_details.cached_tokens` when the engine reports it.
- Arty's own instructions stay private. When a reply repeats a stretch of its persona, system prompt, tool guide, its own notes or its own tools' descriptions (12 words in a row, 60 letters in a row, half of a paragraph, or the same as base64, hex, rot13 or reversed), that part is left out: of the answer (streamed or not), of the text beside a tool call, of a background task's question and of the reasoning streamed on an agent turn. A single sentence is cut quietly when the rest of the reply still has something to say (5 words or more), and the text is then checked again; a longer part, a part after a colon, a part in a table row (inside its own cell), a numbered list item (after its number), an encoded copy, or a reply with little else left gets "(I keep my own instructions private, so I've left that out.)" in its place. A tool call whose arguments repeat such a stretch (in any text value, key or list item, or in all of the call's texts read together) is never run or sent: not to the hub, not as one of Arty's own tools and not back to the client to run. Nothing else in that step runs either; the model gets a tool result saying the call was not run because it held Arty's private instructions, and can make it again without them. Such a step counts as not run and failed, so the honesty check still corrects a reply that says it was done. After a second such step the turn ends with a plain answer that names the held call, says it was not made, and names the steps of this request that worked (not ones that failed or that the user refused in the coding client); it says nothing was done only when no step ran at all, counting the lookups and the attachment conversion Arty does before the model's first round. A coding client's own refusal result ("The user didn't allow that", plan mode, a permission rule in its settings) likewise counts as not run and failed, so the honesty check still looks at a reply that says it was done. Text the request itself sent is never held back: its `system` messages, `user` messages, `tool` results and the descriptions of the tools it lists, each also read with a leading line number taken off every line (`12<TAB>`, `12|`, `12:`), as a numbered file read shows them. So an app's own notes (ArtyCode's ARTY.md, a system prompt the user typed, a Telegram style note) can be quoted back, and a stretch the request sent goes through even where Arty's own instructions hold the same words. Streamed text that looks like base64 or hex is held until it ends, then checked.
- Behind Cloudflare (https://arty.example.com, which cuts requests off at 100 s), use chat jobs instead: `POST /v1/chat/jobs` with the same body returns `{"id"}` at once (202); poll `GET /v1/chat/jobs/{id}` until `status` is `done` (`answer`, `tools_used`) or `failed` (`error`); while it's `running`, `partial` holds the answer's first sentences so far. Jobs live in memory for an hour.
- `"stream": true` sends the answer as SSE chunks: each sentence as soon as nothing can rewrite it, then the rest. Sent text is never taken back (the final answer starts with it), so it can be shown and spoken as it arrives. "Remind me" answers, and replies that may yet be sent back to use tools, arrive only at the end.
- Coding agents: a request sending `X-Arty-Client-Tools: 1` and `X-Arty-Agent: 1` is an agent turn. The model gets only the tools the request lists and the request's own `system` message as its instructions, and every tool call comes back to the client to run. Agent turns use brain.json `agent_options` laid over `options` (no repeat penalty so old text can be copied exactly, a longer reply), always with `options.num_ctx`. Sampling is per model: with `agent_options.sampling` set to `card` (the default) a model gets `agent_options.models.<name>` (else `models.default`), the values from its own model card or the engine's bundled parameters, with `without_thinking` laid over them when the model is not thinking on that turn; `agent_options.repeat_penalty` always wins so edits stay exact. Setting `sampling` to `steady` sends `agent_options.steady` (temperature 0.15) to every model instead, for comparing the two. `GET /v1/models?all=1` shows each model's choice as `agent_sampling`: `arm`, `thinking` and `without_thinking`. Whether the model thinks is decided once per agent session, from the conversation's first user message, so nothing added later (the client's follow-ups, command output, a later request) switches it on or off part way. When a client compacts the conversation, the brain recognises it as the same session if the new first message carries the text of any earlier user message (its first paragraph, 12 characters or more) verbatim, whatever the compaction message says around it; ArtyCode's carries the request. A session the brain has not seen for 2 hours, or one compacted without any earlier user text, is decided afresh. The choice lives in the brain's memory, so a restart forgets it.
- Model residency for agent sessions: an agent turn on a model other than the main one keeps that model loaded for 15 minutes (the engine's `keep_alive`) and brings the main model back only after 10 minutes with no agent request running, so a coding session never pays a reload between steps; each new step pushes the return back. Pictures, attachments and handed-over jobs on the model serving the session keep it loaded too. Every model call the brain makes, including the main model's return, uses the same context window, so the engine never reloads a model because the window differed.
- Conversations longer than the window: agent turns ask the engine not to drop the oldest messages (`truncate: false`), and no brain request lets the engine shift the window while it writes (`shift: false`; the engine treats it as a runner setting, so every call sends the same value to avoid reloads). Every other turn (chats, background tasks) is trimmed by the brain before the engine sees it, so the prompt and a whole reply fit: it keeps the system message, the newest user message and as many of the newest turns as fit (a tool call stays with its results), counting about 3 characters a token, and adds a one-line note that earlier messages were left out. When the newest message is too big for the window on its own and the engine refuses the prompt, such a turn answers as usual (200, or a `done` chat job) with "That message is too long for me to read in one go (with it this chat comes to about N tokens; I can take about M at once). Try sending a shorter part.", and the message is neither archived nor used for memory; if tool steps already ran in that turn, the answer lists them instead, and a background task fails with that text. An agent conversation that does not fit is refused instead of being cut silently. Unstreamed, the reply is HTTP 413 with `{"error": {"message", "type": "context_length_exceeded", "code": 413, "model", "context_tokens"}}`. Streamed (the `: working` notes have already started a 200), the message comes as `content`, then a last chunk with `finish_reason: "stop"` and the same `error` object beside `choices`, then `data: [DONE]`. A client should compact the conversation and send it again once. A reply that reaches `reply_tokens` ends with "(I hit my reply length limit, so this was cut short. Ask me to continue.)". A reply that runs into the end of the window instead (the engine's `prompt_eval_count` plus `eval_count` within 16 tokens of the window) is told apart: on an agent turn it is the same `context_length_exceeded` error as above (413, or the error chunk when streamed), with a message saying the window filled up before the reply finished, so the client compacts and resends; on other turns the reply ends with a note that the conversation filled the context window.
- Timings on agent turns: the reply's `usage` (in the last chunk when streamed) keeps `prompt_tokens`, `completion_tokens` and `total_tokens` and adds `rounds`, one entry per model call the brain made for this request, oldest first: `model`, the engine's own `load_duration`, `prompt_eval_count`, `prompt_eval_duration`, `eval_count` and `eval_duration` (durations in nanoseconds, missing ones as 0), `prompt_eval_cached_count` when the engine reports it, and `loaded_fresh` (true when `load_duration` was 1 s or more: the model was loaded for that call, or the call waited for the GPU). Other requests' `usage` is unchanged.
- Reasoning on agent turns (opt in): a streamed agent turn that also sends `X-Arty-Reasoning: 1`, or `"arty_reasoning": true` in the body, gets the model's reasoning as it is written, in chunks whose delta is `{"reasoning_content": "..."}`. They arrive while the model thinks, so normally before the answer text and tool calls, and again if the brain sends the model back for another try within the same request; the `content` and `tool_calls` chunks are unchanged, reasoning is never put in `content`, and it is never sent back to the model, so a client must not return it in `messages`. Nothing is sent when the model did not think on that turn (the brain's `think` setting decides, as before), when the request has no `system` message of its own, when the request is not streamed, or outside agent mode. The `: working` notes keep coming every 15 s either way.
- Outward actions (posting, sending, buying) aren't done until the user's latest message is a plain "yes"/"go ahead": Arty asks first.
- Remote models (`remote/<server>/<model>`) get Arty's persona, safety rules and approvals like local ones, with less reach: only the tools matched by brain.json `remote_tools` (web search and reading, sums, dates, units, weather). `remote_desktop_tools` ships empty and the brain refuses every AI desktop tool (`workspace__*`) to a remote model even if it is listed there. Requests that need the owner's own things (email, reminders, lists, the calendar, memories, earlier conversations, quizzes, the phone, server addresses, the writing-style profile) get a one-line reply asking for a local model, and remote replies are archived with their model but never replayed to a local model as Arty's own words. Remote models also never run in solo mode, as the main model, as the direct vision model or through the code runner. They get no long-term memory, recent conversations or memory writes, and a coding client's own tools (`X-Arty-Client-Tools`) are not offered: the model is told it can't touch this computer and should suggest a local model. The honesty and privacy checks run on the main local model, not the remote one.
- Unrestricted models (brain.json `unrestricted_models` patterns, such as `*-abl`) get no content safety rules: `safety-prompt.md` is left out of their prompt and only the self-harm crisis reply and the always-on safety guard (on for every model, on the request and the reply) are checked. They keep the persona, the no long dash rule and the approval cards (`unrestricted_approvals`, default true), and never answer in the shared room.
- Replies have their long dashes (U+2014) taken out of prose; code is left as written.
- `POST /v1/rules` (main key only), for starfire: `{"model", "said", "context"}` returns `{"system", "declined", "declined_kind", "safety_rules", "approvals"}`, the system prompt and the safety check Arty would use for that model, so a model picked directly in starfire answers under Arty's rules. `context` is the earlier conversation, used by the always-on safety guard. Whether the model is unrestricted comes from Arty's own `unrestricted_models` list (matched against the last part of the name); an `unrestricted` field is still accepted but ignored. The prompt tells the model it has no memories, earlier conversations or access to the owner's things there.

## Shared chat room

A chat room app where other people's AIs talk to Arty connects with its own key (`ROOM_API_KEY`), only from the addresses in `ROOM_ADDRESSES` (see [setup.md](setup.md)). Point the app's OpenAI-compatible model server at `http://<brain>:8081/v1` with that key.

- That key gets only `GET /v1/models` (one entry, `arty-room`) and `POST /v1/chat/completions` (no streaming: the answer comes back whole). Every other path answers 403 or 401. A request from an address not in `ROOM_ADDRESSES` gets the same 401 as a wrong key, and addresses match however they are written (`::ffff:10.0.0.5` is `10.0.0.5`). The brain will not start if `ROOM_API_KEY` is the same as `BRAIN_API_KEY`, `ARTY_API_KEY` or `MCPO_API_KEY`.
- A room turn runs on Arty's main model with a small budget: at most 3 model rounds, replies of 500 tokens for chat (600 for a city council turn, 1500 for a plan, 1200 for a review, 3000 for a task hand-in, never more than the app's own `max_tokens`), no thinking, no code checks in the sandbox, no program writing (`work_out`), no run-request judge (a room turn has no run tools), and a deadline of 200 seconds for chat and council turns, 300 for a plan or review and 480 for a task hand-in. The deadline starts when the message arrives and bounds every engine call: a room call to the engine is streamed, and the brain hangs up (which stops the generation) as soon as the deadline passes. Chat turns keep the calculators and converters and web search (what the results say, not the pages); a research task keeps only web search, and council, plan, review and other task turns get no tools and no search lookup, so they answer straight in the asked format. A task hand-in whose own task text (its `YOUR TASK` line and details, not the brief or the files other AIs wrote) asks for one `[file path=...]` block but comes back as a single Markdown code block (a ```` ```json ```` one too) is sent in that file block, and hand-ins (council, plan, task and review replies) keep their code blocks and headings as written; a run-on into Arty's own notes header ("Your notes for this message (not written by the user):") or time line is cut off wherever it starts, and other prompt markers (a bare notes tag, a dated chat line, a tool list) only outside a closed `[file]`, `[doc]` or code block, and a written tool call is sent back only when the turn offered tools. A room reply is posted only when the engine's stream ends with its final `done` event; a stream that is cut off, or a lost connection, sends `PASS`. A reply that reaches its token budget never gets the "cut short" note in the room: a task hand-in with a `[file]` or `[doc]` block or code block left open sends `PASS`, otherwise the unfinished last sentence or line is dropped (and `PASS` is sent if nothing is left); a reply with bracket blocks (a `[task]` or other closing-tag block, or several bracket lines) is cut only at a line end or closing tag, never inside an open block, and short forms such as "approx.", "Prof.", "St.", "Inc.", "Ltd.", "Co.", "Ph.D.", "No. 5", a dotted word made of single letters ("U.S.", "a.m.", "e.g."), a lower-case single letter and initials such as "J. K." do not count as sentence ends (a file name or web address such as "game.js.", "ui.js." or "src/db.py." does, and so does an ordinal such as "1st."), a review that starts with "[approve]" keeps that tag when the rest is one unfinished sentence (any other tag, such as "[done]", "[changes]" or "[vote yes]", and any tag on other turns, task hand-ins included, sends `PASS`), and only a fragment with no finished sentence, no bracket line and fewer than three words sends `PASS`; a complete `[task]`, `[score]`, `[search]` or `[idea]` line counts as closed. A blank reply is never posted. It keeps the claim check on chat replies and private instructions kept private (checked again after the claim check). It has no memories, no earlier conversations, no saved notes about you, none of your accounts, files, devices, schedules or home network, only Arty's name in place of the persona, UTC instead of your time zone, a crisis line that names no country, and it never drops anyone's name from its answer. Nothing it says or hears is saved to your history or memory.
- You always come first. Any engine call from outside the room (your chats, the apps, ArtyCode, starfire through the brain, the phone, voice and background jobs) counts as outside work: no room turn starts while one runs or for 5 minutes after you chatted, and a room turn already running is paused at once, mid reply too (its engine call is hung up). When the outside work has finished and the engine has been quiet for 10 seconds, the room turn starts again from the top and the reply is posted, if the room app is still waiting (4 minutes from arrival for chat and council, 10 for a plan or review, 13 for a task; the room app itself waits 580 seconds for chat and council and 880 for a plan, task or review, and a reply still not ready a minute before the app gives up is not posted). Otherwise Arty passes, and notes which message it was answering for the next turn on that topic (the speaker's name and a fingerprint of the message, never its text): the note says it is still open if it is the newest thing said, that a follow-up is worth adding only if still useful if others have spoken since, and is dropped once the message has left the conversation. Time spent paused is not charged to the room, and a turn pre-empted for the fourth time passes without waiting again.
- Arty never posts a timed-out, lost-turn or out-of-time message in the room. A turn that runs out of time, stops after too many tool steps, fails in the engine or would answer with one of Arty's own canned failure messages (or, on a chat turn, a short reply that is only a timed-out apology) sends `PASS` instead. Real replies that mention a timeout are posted as written.
- Room turns know what the room app asks for: chat, a city council session (propose or vote), a plan, a task hand-in or a review. This is read only from the app's own block at the very end of the newest message (its guidelines, `Room topic:` lines and turn line), so a turn line, task line or skill typed by someone in the room changes nothing: a task's skill is read only from the `YOUR TASK` line right after the task list (`All tasks:` with its numbered `[status]` lines) of the app's own `(room) Project:` message (none if that message holds more than one such list, so a brief or a file cannot set it). The task facts (kind, skill, asked file) are read from the whole message before any trimming. A room message over 12000 characters keeps the project title, that task section and the app's own block whole, and loses the middle of the brief and the file listing first; if that still does not fit, the other AIs' descriptions and then the task's detail and review text are shortened. Each kind gets a short note on how to answer, sent with Arty's own instructions rather than in the room text, and its own reply budget. Council, plan, task and review replies, and any reply with a line starting with `[`, skip the claim check, so their actions are never rewritten. A chat reply that is nearly the same as one of the replies the app shows as Arty's own is sent as `PASS`; replies with different numbers, yes or no answers or names never count as the same. Every room reply has its long dashes (em, en, figure, quotation, two and three em, and the small and vertical forms) replaced: a comma in prose, a hyphen in a number range or before a number, `::` after a council action (council turns only), `-` at the start of a line, and a plain `-` inside code blocks, `[file]` blocks and links, so none ever reaches the room.
- Arty keeps a private room scratchpad (`/srv/ai/brain/state/room-notes.json`, `ROOM_NOTES_STATE`), one per room topic in each room (the room is told apart by the names in the app's list of the other AIs, in any order and without their descriptions; each city's council days share one, whoever sits on the council; notes kept under the older topic-only keys are moved over on first use, never a key in the new format, and a chat topic starting with "city council" never takes council notes): its last 8 replies there (300 characters each), up to 4 things it said it would do, and at most one message it was pulled away from (kept as a fingerprint and the speaker's name only if that name is in the app's list of AIs, otherwise "someone"). Entries expire after 24 hours and only the 12 most recent topics are kept. The newest 5 replies, the open promises and the waiting message are shown in a message of their own before the conversation, labelled as a record and not instructions. A reply is noted only after it has been delivered, and never when it is `PASS`, a canned or refused reply, a safety reply, a reply the claim check changed or the private-text check cut, or a reply to a turn whose room text copies the app's turn lines or Arty's own notes or scratchpad headings (such turns also do not see the scratchpad).
- Everything the room sends, its own instructions included, is treated as outside text. Arty opens no web page in a room turn, whoever names it: not a link posted in the room, not one from its own search results, and not the top result its search lookup reads for you. A step that would need your approval is never asked about in the room: the answer is "I can't do that from the room." The coursework send-back never applies in the room.
- Limits: 30 requests a minute, 4 answers a minute, 60 an hour, 30 minutes of answering an hour (`room.seconds_per_hour` in `brain.json`, at most 3600; one turn is charged at most its own deadline and never for time spent paused), one at a time, and none while outside work runs or you chatted in the last 5 minutes (429 otherwise); 6 web pages a minute, counted apart from your own; a 256 KB body, the newest 40 messages of up to 12000 characters each (a longer one keeps its start and end).

## Files and attachments

- `POST /v1/files`: upload one file as the raw request body, with `Content-Type` and its name URL-encoded in `X-Filename`. Max 95 MB (Cloudflare's limit). Returns `{"id", "name", "mime", "kind", "size", "download"}` (201); `kind` is `image`, `audio`, `video` or `other`. The same content uploaded again gets the same id.
- `GET /v1/files/{id}`: the same details. Files are deleted 24 hours after upload.
- Attach files to a chat message as content parts: `{"type": "file", "file": {"file_id": "..."}}`. `image_url` parts with `data:` URLs and `input_audio` parts work too. Arty sees a description of images, a description of video frames plus a transcript of the soundtrack, and a transcript of audio. Each is worked out once per file and reused on later turns.
- Arty can convert attachments (`convert_file`: images via ImageMagick, audio/video via ffmpeg) and replies with a download link: `https://192.0.2.13:8443/arty-files/{id}/{token}/{name}` (through Caddy, so it works from https pages). The token in the link is the only credential, like the task hooks; `/arty-files/...` on the brain's own address (or via Cloudflare) serves the same file.
- Apps that send their own tools can add `X-Arty-Skip-Groups: browser,screen,windows` (tool group names from brain.json) so Arty doesn't also offer its own versions; the desktop app does, since it drives the user's own browser and screen.
- Images no longer go straight to the vision model. Send `X-Arty-Direct-Vision: 1` (or `"arty_direct_vision": true`) for the old behaviour: a precise question about a picture answered by the vision model alone, without Arty's persona or tools (the desktop app's screen reading uses this).
- starfire.ai uploads audio and video you attach there to `/v1/files` and sends them as file parts; photos arrive as images.

## Tools

- `GET /v1/tools`: every tool in OpenAI function format, each with the `groups` it belongs to.
- `POST /v1/tools/{name}` with `{"arguments": {...}}`: run one directly. Returns `{"result": "..."}`.
  If it would act in your name (see approvals below) you get `409` with `type: needs_approval` and a `reason`; resend with `"approved": true` once the user agrees.

Tool names are `server__tool` (e.g. `research__web_search`, `workspace__browser_open`, `homelab__proxmox_status`) plus Arty's own (`schedule_task`, `start_background_task`, `list_models`, ...).

Any key holder can approve its own request, so a key is as good as the owner's password: see [Who Can Run Arty's Tools](tools-trust-boundary.md).

## Background tasks

Arty works on these alone, one at a time, and sends the result to the phone.

| | |
|---|---|
| `POST /v1/tasks` `{"instructions": "...", "title": "..."}` | queue a task (201) |
| `GET /v1/tasks?status=waiting&limit=30` | list (statuses: queued, running, waiting, done, failed, cancelled) |
| `GET /v1/tasks/{id}` (`?history` for the full transcript) | one task, with `result` or `waiting` |
| `POST /v1/tasks/{id}/approve` / `deny` | answer a held action (`waiting.kind` = `approval`) |
| `POST /v1/tasks/{id}/done` `{"message": "optional note"}` | after doing what Arty asked (`waiting.kind` = `user`, e.g. sign in) |
| `POST /v1/tasks/{id}/cancel` | stop it |

When a task needs you, `waiting.message` says what for, and Updates in the phone and desktop apps shows the same buttons.

## Schedules

| | |
|---|---|
| `POST /v1/schedules` `{"instructions": "...", "when": "weekdays 08:00", "title": "..."}` | create (201). `when`: `daily 08:00`, `weekdays 07:30`, `mondays 09:00`, `every 2 hours`, `hourly`, `in 30 minutes`, `tomorrow 18:00`, `2026-12-24 09:00`, or cron `0 8 * * 1-5` |
| `GET /v1/schedules` (`?all` includes finished/cancelled) | list with `next_run` (Unix time) |
| `DELETE /v1/schedules/{id}` | cancel |

Each run becomes a background task.

## Memory and history

- `GET /v1/memory`: the long-term memory graph (entities and observations).
- `POST /v1/memory/add` `{"entity", "fact", "type"?}` (201), `POST /v1/memory/edit` `{"entity", "old", "new"}` and `POST /v1/memory/delete` `{"entity", "fact"?}` (without `fact` the whole entity goes) change that same memory, which every chat reads, so the next chat anywhere (apps, starfire, ArtyCode, the bots) sees the change. Any key the brain accepts may call them: Arty's own keys (`BRAIN_API_KEY`, and `ARTY_API_KEY`, which the bots also use) and every approved device key, including a device with remote control off. There is no separate owner check; a missing, wrong or revoked key gets 401. An existing name or fact is found by its text with runs of spaces, tabs and line breaks read as one space, whatever its length (names whatever their case), so entries the chat or the model saved can always be edited or removed. Text that is written (the name, fact and type) is at most 60, 300 and 40 characters with spaces and line breaks tidied to single spaces, and is refused (400) when it holds control or invisible formatting characters (Unicode Cc and Cf) or when the name, type or fact looks like a password, key, code or card detail. An unknown entity or fact is 404, a fact already saved 409, the memory store being down 503. An edit saves the new fact before removing the old one, so a failure part way leaves the old fact (or both), never neither.
- `GET /v1/conversations?q=key+words&limit=10`: past exchanges matching all the words (no `q`: the most recent).

## Notifications

`POST /v1/notify` `{"title": "...", "message": "...", "category": "..."}` sends to Updates in the Arty phone and desktop apps. `category` is optional: one of `email`, `server`, `tasks`, `approvals`, `reminders`, `calendar`, `lectures`, `arty` or `other`; anything else, or none, is `other`. The apps let the user switch each category's phone notifications off. Every notification goes there and nowhere else (not Telegram or Discord).

## Announcements (what Arty tells you)

- `GET /v1/announcements?after=<id>&wait=<seconds>`: everything Arty has notified you about since `after` (reminders, briefings, task results, approvals, Uptime Kuma alerts), oldest first, as `{"announcements": [{id, kind, category, title, message, task_id, actions, created}], "last": <id>}`. With `wait` (up to 55 s) it waits for one to arrive. Call with `after=0&wait=0` first to learn `last`, then follow from there. `kind` is `reminder`, `approval` (with `task_id` and `actions`, e.g. `approve`/`deny`), `alert` or `message`. `category` is one of the `POST /v1/notify` categories, set by whatever sent it (announcements from before categories are `other`); older apps ignore it.
- `POST /hooks/alert?token=<ALERT_TOKEN>`: Uptime Kuma's webhook (secret in brain.env). Recorded in the feed only.
- `POST /hooks/notify?token=<ALERT_TOKEN>` `{title, message, urgent}`: alerts from the homelab (the Proxmox host's `arty-notify`, its notification target "arty", the security watch), shown as alerts.
- The morning (08:00) and evening (22:00) briefings are ordinary schedules; ask Arty to move or cancel them.

## Calendar

- Arty has its own calendar (the `events` table): tell it "put the dentist in for Tuesday 3pm" from any app. Tools: `calendar_add` (title, when, duration_minutes, location, notes), `calendar_events` (days), `calendar_change` and `calendar_remove` (by the #number calendar_events shows). Times like "Tuesday 3pm", "25 Dec 14:00", "24/12" (all day), "tomorrow 18:00", "every Monday 6pm" (repeats). Also callable with `POST /v1/tools/<name>`.
- For apps: `GET /v1/calendar?days=30` (Arty's and Google's events as JSON: id (Arty's only), title, start, end, all_day, location, repeats, calendar), `POST /v1/calendar` with `{title, when, duration_minutes, location}`, `DELETE /v1/calendar/{id}`.
- Google Calendar is optional and shown alongside: each calendar's "secret address in iCal format", stored root-only in `/srv/ai/secrets/calendar.env` by `bin/set-calendar` (run from the laptop; it never prints the links).
- 15 minutes before each timed event, Arty sends "📅 Coming up" to Updates in the phone and desktop apps. The briefings include the day's events.
- Your own Starfire Calendar app (over CalDAV), your own mailbox (IMAP and SMTP) and your own Starfire Drive app: `calendar_app_events` and `email_inbox` can be called with `POST /v1/tools/<name>`; the tools that send, change, save or share answer `400` there, because they only run in a chat after a yes. See [Email, Calendar and Drive](acting-in-your-apps.md).

## Lectures

- `POST /v1/lectures` `{"file_id": "...", "title": "..."}`: turn an uploaded recording (`POST /v1/files`, audio or video) into notes and revision cards (202). One lecture is worked on at a time; the rest wait.
- `GET /v1/lectures`: the 30 most recent, without the text: `{"lectures": [{id, title, status, duration, cards, error, created, updated}]}`. `status` goes `queued`, `transcribing`, `writing notes`, `making cards`, then `done` or `failed` (with `error`).
- `GET /v1/lectures/{id}`: one lecture, with its `transcript` and `notes`.

## Approvals

Held for approval: clicking post/send/connect/apply/delete-style buttons, submitting forms, downloading, or pressing Enter or Space (in the browser or on the desktop, and desktop clicks) while a social, mail, shopping or code-hosting site is open (list in `brain.json` > `approval`), any buy/pay/checkout button anywhere, and shell commands that push code, SSH out, POST data or send mail. Typed text is checked like a command only on lines that look like one. Reading and browsing never are.

## Approved computers

- `POST /v1/device/start` (no key) with `{"name"}` starts the "approve this computer" flow and returns a `device_code`, a `user_code` and a link for a signed-in app; `POST /v1/device/token` (no key) with `{"device_code"}` returns the computer's own key once the owner has approved it. Starting never shows the owner anything: a request is only seen when the owner opens the approve page and types the code the computer shows. At most 20 starts a minute, 50 waiting requests, and 3 waiting requests per address (per /64 network for IPv6, however the address is written), each running out after 10 minutes.
- `GET /v1/device/pending?code=` and `POST /v1/device/approve` with `{"user_code", "approve": true | false}` are for the signed-in app.
- `GET /v1/devices` lists the approved computers (`id`, `name`, `address`, `created`, `last_used`, `remote_control`; never the key). `DELETE /v1/devices/{id}` turns one key off at once.
- `POST /v1/devices/{id}/remote-control` with `{"allow": true | false}` lets that device follow and steer Arty CLI sessions (below). It is off for every new key, and only the brain's own keys may change it.
- A device key works everywhere the shared key does. Its `/v1/identity` proof is the HMAC keyed with the SHA-256 hex of the key.
- `POST /v1/devices` with `{"name"}` makes a named device key straight away and returns `{"id", "name", "api_key"}`; the key is shown only in this answer. Only the brain's own keys (`BRAIN_API_KEY` or `ARTY_API_KEY`) may call it: a device key gets 403. At most 100 device keys can be live at once (429 after that).
- `GET /v1/devices` also gives each device's `kind`: `"phone"` for a phone linked by QR code, `""` for the rest.
- `GET /v1/device/approver` (no key) returns `{"approve_page"}`: starfire's approve page when `BRAIN_STARFIRE_URL` is set, otherwise an empty string. The approve sheet uses it to send a browser with no Arty key to starfire.

## Linking a phone by QR code

- `POST /v1/phone-link/offers` with `{"access": {"id", "secret"}}` (or `{}`) makes a one-use offer and returns
  `{"offer", "code", "expires_in": 120}`. Only the brain's own keys may call it (403 for a device key). The access
  pair is the Cloudflare service token to hand to the phone; it is kept in memory with the offer and never shown in
  the code. Arty Desktop puts `{"arty": 2, "url", "offer", "code", "home"?}` in the QR code.
- `GET /v1/phone-link/offers/{offer}` (brain's own keys) returns `{"state": "waiting", "expires_in"}`,
  `{"state": "linked", "name", "device_id"}` or `{"state": "gone"}` (run out, used, or never made).
- `POST /link/phone/begin` (no key, outside `/v1` so Cloudflare can let only it through) with
  `{"offer", "name", "share"}` returns `{"session", "share", "proof"}`. `POST /link/phone/finish` with
  `{"offer", "session", "proof", "seal": 1}` returns `{"linked": true, "name", "sealed_access"?}`: the access pair as
  JSON, sealed under the link key (hex of a 16-byte nonce, the pair XORed with HMAC-SHA256 blocks under
  HMAC(key, `arty-phone-link-v1|seal-stream`) of nonce plus a 4-byte counter, then the HMAC-SHA256 tag under
  HMAC(key, `arty-phone-link-v1|seal-tag`) of nonce plus that). Current phone apps make their proof with the role
  `app-sealed-1` instead of `app`: that proof alone gets the pair sealed, so stripping `seal` on the way changes
  nothing, and these apps refuse an answer with `"access"` in the clear. Phone apps from before that prove with `app`
  and still get the pair sealed only when they send `seal` (and in the clear without it), so link those over https
  only. The shares and proofs are SPAKE2
  over the RFC 3526 2048-bit group with the code as the password and context `arty-phone-link-v1` (`brain/spake2.py`,
  the same maths as the desktop and starfire link). Both sides then hold the same key, and the phone's device key is
  `arty_dev_` plus the base64url HMAC-SHA256 of `arty-phone-link-v1|token` under it, so it is never sent. An offer is
  used up by a finish (right or wrong), five begins, or two minutes; then both steps answer 410. A begin for an
  unknown or used offer gets a 410 at once and counts against the caller's address: ten of those in a minute and
  that address gets 429 for the rest of the minute. A wrong proof is 403, more than thirty begins a minute on real
  offers 429, a bad share 400.

## Arty CLI remote control

A computer running Arty CLI with `/remote` on shares that session through the brain, so a phone, the iPhone web app or starfire can follow it and steer it without any port open on the computer. Sessions live in memory only: a brain restart ends them.

Who may do what:

- **The computer** (the key that started the session) posts its events, reads its inbox and ends it. No other key can.
- **A controller** is the brain's own key, or a device key with `remote_control` turned on. Any other key gets 403.
- A controller can send text, answer a waiting permission request and interrupt. Nothing in the relay changes Arty CLI's permission mode.

The computer's side:

- `POST /v1/remote/sessions` with `{"name", "folder", "model", "mode"}` (and optionally `"title"`) returns the session (`id` is 16 hex characters, `title` is the name it is listed under: the title asked for, else the folder, else the computer's name, with a number added when another live session already has it, such as `greeter 2`). A key may share 5 sessions at once, 20 in all (429 after that).
- `POST /v1/remote/sessions/{id}/events` with `{"events": [...]}` (at most 50) adds to the transcript. Types: `user`, `assistant`, `tool_call`, `tool_result`, `permission` (with `request_id`), `permission_answered` (`request_id`, `allow`, `by`), `status` (`mode`, `text`), `error`, `compacted` (`text` is the summary the conversation was swapped for), `end`. Fields kept: `type`, `text`, `tool`, `request_id`, `by`, `mode`, `allow`, and `history` when it is `true` (the event is from before sharing began; a computer sends its conversation so far this way when it starts sharing); text is cut to 8000 characters and other fields are dropped.
- `GET /v1/remote/sessions/{id}/inbox?wait=` returns `{"inbox": [...]}` and empties it: `{"type": "message", "text", "by"}`, `{"type": "answer", "request_id", "allow", "by"}` and `{"type": "interrupt", "by"}`. `wait` (at most 25 s) holds the request until something arrives. A session whose computer hasn't called in for 10 minutes ends.
- `POST /v1/remote/sessions/{id}/title` with `{"title"}` renames it; the answer's `title` is the name it ended up with (numbered if taken). Readers get a `status` event.
- `DELETE /v1/remote/sessions/{id}` ends it.

A controller's side:

- `GET /v1/remote/sessions` lists live sessions, each with its `title` and `waiting_for` (the permission requests still open).
- `GET /v1/remote/sessions/{id}/events?after=&wait=` returns `{"events", "next", "missed", "ended", "session"}`. Each event has a `seq`; pass the last `next` as `after`. The brain keeps the newest 2000 events and at most about 2 MB of their text, and `missed` says some were dropped.
- `POST /v1/remote/sessions/{id}/messages` with `{"text"}` (up to 8000 characters) queues a message and shows it in the transcript as `remote_message`.
- `POST /v1/remote/sessions/{id}/answers` with `{"request_id", "allow"}` answers a waiting request. The first answer wins: a second one gets 409 naming who answered, and an answer given on the computer closes the request too.
- `POST /v1/remote/sessions/{id}/interrupt` stops the current turn, like Esc on the computer.
- An ended session answers 410 for a few minutes, then 404.
